Code Mode 是什么，以及我们会遇到什么

平时模型是「一次调一个工具」。code mode 让它「写一段代码，代码里去调工具」。就这一个区别，但会带出几种新情况。

一两种入口，差别只有一层

左边是平常的调用，右边是 code mode。注意结果最后到达模型手上的东西不一样。

直接调用 平常

模型
↓
bash(...)
↓
真实进程
↓
结果直接回到模型眼前

脚本调用 code mode

模型
↓
codemode(一段 JS)
↓
沙箱里执行
↓
代码里调 bash(...)
↓
只有 text() 出去的内容回到模型

二最关键的一句话：沙箱里的东西，模型看不见

这不是附加特性，是 code mode 存在的理由。它就是为了让中间过程不占模型的上下文。

沙箱内部 · 模型完全看不到

代码里调了 20 次工具，每次都返回了几百行。这些全部留在沙箱里。

模型不会收到这 20 份结果。它不知道调过什么，也不知道返回了什么，除非脚本主动往外送。

const a = await tools.bash({ command: "npm test" });
const b = await tools.bash({ command: "npm run lint" });
// a 和 b 里可能是几百行日志，模型一个字都看不到

text(a.exit_code === 0 ? "测试过了" : "测试挂了");  // 只有这行能出去
出口只有一个。脚本用 text() 送出去的内容，加上 console 输出和脚本的返回值。
这一点会引出后面很多情况。凡是「模型应该知道但脚本没往外送」的信息，模型就是不知道。

三同一个 bash，在脚本里返回值不一样

工具没变，只是交给谁变了。交给模型是文字，交给脚本是对象。

直接调用在脚本里调用
拿到什么 一段给人看的文字 一个对象，比如 { output, exit_code }
非零退出 算失败，标红 不算异常，exit_code 是 1 而已，脚本继续跑
界面上的实时进度 有，一行行刷出来 没有，等脚本跑完
交接时的返回 文字提示还带了 task_id { status: "running", task_id, log_path }

四六种会遇到的情况

前两个是正常的，后四个是需要知道原因的。绿色正常，黄色会让人误判，红色真出事。

01

脚本里跑一个短命令

正常 
const r = await tools.bash({ command: "git status --short" });
text(r.output);

两秒跑完，结果进沙箱，text() 把内容送出去。模型看到的那几行和直接调用几乎一样。

这条没问题，和平常没区别。

02

脚本里跑长命令，脚本乖乖结束

正常 
const r = await tools.bash({ command: "npm test" });
if (r.status === "running") text("后台任务 " + r.task_id);
else text("退出码 " + r.exit_code);
脚本
30s 结束
命令
第 30 秒交接，继续跑到 130s
模型
先收到 task_id，之后收到完成通知

这是设计好的路径。第 30 秒 bash 交接，脚本拿到 task_id 就自己结束了，命令继续跑完。

完成时 Pi 发一条通知回原会话。脚本里那行 text 和后来的通知，会是同一件事的两次告知。重复但不丢，这是已知取舍。

03

脚本超时，命令还没到交接的点

会误判 
// @options: {"timeout_ms": 20000}
const r = await tools.bash({ command: "npm test" });
脚本
20s 被杀
命令
同一秒被杀，没活到第 30 秒

脚本设了 20 秒上限，但 bash 要到第 30 秒才交接。第 20 秒脚本被掐，里面还在飞的调用跟着被取消，进程组一起被杀。

模型很容易以为「脚本超时了，但命令还在后台跑」。实际上命令已经死了。这是六个里最需要知道的一个。

04

写了调用，但忘了 await

立刻死 
tools.bash({ command: "npm run build" });   // 少了 await
text("构建已在后台启动");

脚本结束时，没人等的 promise 被直接丢弃。调用被取消，命令当场被杀，往往一行输出都还没产生。

那行 text 会让模型以为构建在跑，其实连启动都没完成。这是模型自己写错，但后果是它看不到的。

05

用一个循环开出一堆后台任务

会刷屏 
const pkgs = ["a", "b", "c"];   // 实际可能 20 个
const out = await Promise.all(
  pkgs.map(p => tools.bash({ command: `npm run build -w ${p}` }))
);

这是 code mode 真正的好处，20 条命令并行，模型只看汇总。但如果每条都超过 30 秒，就会产生 20 个后台任务。

之后会有 20 条完成通知陆续回来。我们现在没有任务数量上限，Codex 那边是 64 个并会淘汰最久未用的。

06

脚本里自己等结果

会重复 
const r = await tools.bash({ command: "npm test" });
const f = await tools.bash_task({ task_id: r.task_id, wait_seconds: 60 });
text(f.output_tail);

脚本等到终态，把尾部打印出来。模型从脚本输出里看到了结果。

但 Pi 那边仍然会发完成通知，因为嵌套调用的结果没有作为工具结果出现在模型眼前，Pi 无法判断模型是否真的看到了。结果是同一份内容出现两次。

五四家怎么做，我们站在哪

这一栏之前那份研究档案漏了，只看了 shell 链路，没看 code mode。

产品脚本里能调 shell 吗怎么处理脚本自己也跑不完的情况
Codex
exec / wait		 能，tools.exec_command(...) 加了一整套「等脚本」的机制。wait(cell_id)，脚本可以挂起再续
OpenCode
execute		 不能，shell 标了 codemode:false 不需要。shell 根本进不了脚本，这类问题不存在
Unreal Agent 没有 code mode 不适用
Pi（我们）
codemode		 能 没有脚本级挂起。脚本必须一口气跑完，跑完就取消还在飞的调用
Codex 之所以那么复杂，是因为它支持「脚本挂起、稍后接着跑」。我们没有这个能力，所以那套 cell_id 机制不需要。 上面六个情况里，第 3、4 两个的根因就是「脚本不能挂起，只能跑完或被杀」。

六结论

代码不用改。归属校验、交付去重、交接之后的取消隔离，这三条我在代码里确认过是对的。

要补的是提示词里的一句，大意是「在 code mode 脚本里，脚本结束或被取消时，尚未交接的命令会被一起杀掉。需要它在后台继续，就让命令先跑到交接」。

再往下是观察，不是设计。循环开 20 个任务这种，真遇到了再加进程表上限。现在加是猜。

事实来源：本地 ~/20-dev/90-third-party-repos/ 下的 codex 04e365c69、opencode2 843a6c514e、unreal-agent a5f3fd1，以及 Pi 1.6.0 的 dist/extensions/codemode/execute.js。

取消传播的结论来自读 execute.js:455-500 和 dist/core/nested-tool-calls.js，没有实际跑 code mode 脚本验证。
